Complete Guide to Playwright MCP Browser Automation

Published July 6, 2026 · By SmartX QA Team · 7 min read

Browser automation has traditionally required writing scripts with explicit selectors — CSS selectors, XPaths, or data-test attributes. The Model Context Protocol (MCP) introduces a fundamentally different paradigm where test agents interact with web pages through semantic descriptions rather than DOM selectors.

What Is Playwright MCP?

Playwright MCP is a server that exposes browser automation capabilities through the Model Context Protocol. Instead of writing page.click('#submit-btn'), you describe what you want to interact with: browser_click({ target: 'Submit button' }). The MCP server uses the page's accessibility tree to resolve your description to the correct element.

This approach offers several advantages for QA automation. Tests become more resilient to UI refactoring because they don't depend on implementation details like CSS classes or element IDs. They also read more like natural language test steps, making them easier for non-technical stakeholders to review.

Core Interaction Patterns

Navigation and Snapshots

Every interaction starts with understanding the current page state. The browser_snapshot tool captures the accessibility tree — a structured representation of all interactive elements on the page. Each element gets a unique reference that you can use in subsequent actions.

// Take a snapshot to see what's on the page
browser_snapshot()

// Navigate to a URL
browser_navigate({ url: 'https://staging.example.com/login' })

// Wait for specific content to appear
browser_wait_for({ text: 'Welcome back' })

Form Interaction

Filling forms is one of the most common testing tasks. Playwright MCP supports bulk form filling, which is faster and more reliable than filling fields one at a time.

// Fill multiple form fields at once
browser_fill_form({
  fields: [
    { target: 'Email input', name: 'email', type: 'textbox', value: 'test@example.com' },
    { target: 'Password input', name: 'password', type: 'textbox', value: 'SecureP@ss123' },
    { target: 'Remember me checkbox', name: 'remember', type: 'checkbox', value: 'true' }
  ]
})

Assertions via Snapshots

Instead of traditional assertions like expect(element).toHaveText(), MCP-based tests verify state by taking snapshots and examining the accessibility tree. This is more holistic — you see the entire page state, not just the element you're checking.

Real-World Example: Testing an OAuth Flow

One of the trickiest automation scenarios is OAuth flows, where you navigate across multiple domains (your app, Google/Microsoft login, consent screen, redirect back). Here's how we handle it with MCP:

// 1. Start on app's connection page
browser_navigate({ url: 'https://staging.app.com/connectors' })

// 2. Click the connect button
browser_click({ target: 'Connect Google Search Console button' })

// 3. Google OAuth page loads — wait for it
browser_wait_for({ text: 'Sign in with Google' })

// 4. Fill Google credentials
browser_fill_form({
  fields: [
    { target: 'Email or phone', name: 'email', type: 'textbox', value: 'test@gmail.com' }
  ]
})
browser_click({ target: 'Next button' })

// 5. Handle consent
browser_wait_for({ text: 'wants to access your Google Account' })
browser_click({ target: 'Allow button' })

// 6. Redirected back — verify connection
browser_wait_for({ text: 'Connected' })

Tips for Reliable MCP Automation

After running thousands of MCP-based tests, we have compiled practical tips that improve reliability. Always take a snapshot before interacting with elements — the page may have changed since your last snapshot. Use browser_wait_for before assertions to handle async loading. Prefer browser_fill_form over individual browser_type calls for multi-field forms.

When elements have ambiguous descriptions (multiple "Submit" buttons on a page), add context from parent elements: Submit button in the payment form rather than just Submit button.
