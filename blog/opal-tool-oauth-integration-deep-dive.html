OAuth Integration Deep Dive for OCP Tool Apps

Published July 4, 2026 · By SmartX QA Team · 8 min read

Optimizely's OCP (Open Commerce Platform) supports two fundamentally different OAuth patterns for tool apps. Understanding the distinction between app-managed and platform-managed OAuth is critical for QA engineers testing third-party integrations through the Opal conversational interface.

Two OAuth Architectures

When an OCP tool app needs to access a third-party API on behalf of a user, it must obtain OAuth tokens. How those tokens are obtained, stored, and refreshed defines the app's authentication architecture.

App-Managed OAuth in Detail

With app-managed OAuth, the tool app contains all the authentication logic. The app defines a settings form (forms/settings.xml) where users enter their OAuth Client ID and Client Secret. When the user clicks "Connect", the app's lifecycle handler (onAuthorizationRequest) initiates the OAuth flow, and the resulting tokens are stored in storage.secrets.

The app's ready() endpoint checks whether valid tokens exist in storage. If tokens are expired or missing, ready() returns false, and Opal prompts the user to re-authorize.

// App-managed ready() — validates token
async ready(): Promise<ReadyResponse> {
  const secrets = await this.storage.secrets.get();
  if (!secrets?.access_token) {
    return { ready: false, reason: 'Not connected. Please authorize in Settings.' };
  }
  return { ready: true };
}

Platform-Managed OAuth in Detail

With platform-managed OAuth, the app declares its authentication requirements but does not handle tokens at all. The Opal platform manages the entire OAuth lifecycle — from the initial authorization flow to token storage and refresh.

The app declares authRequirements in each tool's configuration, specifying which Auth Provider and Scope Bundle it needs. When the tool is invoked, Opal checks if the user has an active connection for that provider and scope. If yes, Opal injects a fresh access token into the tool's authData parameter. If no, Opal prompts the user to connect.

// Platform-managed authRequirements declaration
export const gscAuthRequirements = [
  {
    provider: 'opal_tool_google_search_console',
    scopeBundle: 'search_console',
    required: true,
  },
];

// Platform-managed ready() — always true
async ready(): Promise<ReadyResponse> {
  return { ready: true };
}

Auth Providers and Scope Bundles

For platform-managed OAuth, two entities must be configured on the Opal platform before the app can authenticate users.

Auth Provider

An Auth Provider represents a third-party OAuth service (Google, Microsoft, Zoom, etc.). It contains the OAuth configuration: authorization URL, token URL, revoke URL, and the OAuth client credentials (Client ID and Secret). Auth Providers are global — one provider can serve multiple apps.

Scope Bundle

A Scope Bundle maps a logical capability name to specific OAuth scopes. For example, the search_console scope bundle maps to Google's https://www.googleapis.com/auth/webmasters scope. The bundle name must exactly match what the app declares in its authRequirements.

The most common QA failure we encounter is a scope bundle name mismatch. The app code declares scopeBundle: 'search_console' but the platform has a bundle named gsc_access. The OAuth flow completes but tools fail because Opal cannot find the matching scope bundle for the app's request.

QA Testing Strategies by OAuth Type

Testing App-Managed OAuth

For app-managed OAuth, focus on the settings form and token lifecycle. Verify that credentials entered in the settings form are correctly stored in storage.secrets. Test the OAuth redirect flow — enter credentials, click connect, complete Google login, verify redirect back to the app. Test token expiry by waiting or manually revoking the token, then verifying that ready() returns false and the app prompts for re-authorization.

Testing Platform-Managed OAuth

For platform-managed OAuth, focus on the Connectors tab flow and the auth provider configuration. Verify that the connector appears in the Connectors tab (feature flag may need to be enabled). Test the connect flow — click Connect, complete OAuth, verify Connected status. Test that the app receives valid authData by invoking a tool and checking the response. Test token revocation by revoking access in Google Account settings and verifying the app returns a clear error, not a crash.

Common QA Pitfalls

We have documented the most frequent issues our QA team encounters when testing OAuth integrations. Wrong redirect URI is the number one cause of OAuth failures — each environment (staging, integration, production) has a different redirect URI pattern. Missing API enablement on the GCP project causes cryptic 403 errors after a successful OAuth flow. Test user limitations in GCP Testing mode mean tokens expire after 7 days, causing sudden test failures.
